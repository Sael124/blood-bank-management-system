# BECS — מערכת ניהול בנק הדם

> גרסה באנגלית, עם צילומי מסך ותרשים ארכיטקטורה: [README.md](README.md)

תוכנה לניהול בנק דם לאומי, שנכתבה כמטלה בקורס מבוא לתוכנה ביו־רפואית.

המערכת מנהלת קליטת תרומות דם, ניפוק מנות בשגרה לחדרי ניתוח וטראומה, וניפוק חירום
באירוע רב נפגעים (אר"ן), לצד תיעוד מלא של כל פעולה והגבלת גישה לפרטים מזהים של תורמים.

---

## דרישות מוקדמות

| רכיב | גרסה שנבדקה |
|---|---|
| Python | 3.11 |
| SQL Server | Express (מופע `SQLEXPRESS`) |
| ODBC Driver for SQL Server | 18 |

הדרייבר של ODBC מותקן בדרך כלל יחד עם SQL Server. אפשר לבדוק זאת בעזרת הפקודה
`Get-OdbcDriver` ב-PowerShell.

## התקנה והרצה

```powershell
pip install -r requirements.txt
python main.py
```

בהרצה הראשונה המערכת יוצרת את בסיס הנתונים `BloodBank` ואת כל הטבלאות בעצמה,
ויוצרת שלושה חשבונות הדגמה. לאחר מכן יש לפתוח בדפדפן את הכתובת:

```
http://127.0.0.1:5000
```

הגישה למערכת דורשת התחברות. חשבונות ההדגמה מופיעים גם במסך הכניסה:

| שם משתמש | סיסמה | תפקיד |
|---|---|---|
| `admin` | `Admin123!` | מנהל מערכת — משתמשים, מטא-דאטה, כל פעולה |
| `operator` | `Operator123!` | עובד בנק הדם — קליטה וניפוק |
| `researcher` | `Research123!` | סטודנט מחקר — מלאי מנוקה מפרטים מזהים |

### נתוני הדגמה

כדי למלא את בנק הדם בתרומות לדוגמה, בהתפלגות סוגי הדם בישראל:

```powershell
python tools/seed_demo_data.py        # 100 מנות (ברירת המחדל)
python tools/seed_demo_data.py 250    # מספר מנות אחר
```

הכלי מחלק את המנות בין סוגי הדם לפי אותה טבלת שכיחות שהאלגוריתם עצמו משתמש בה, ולכן
המלאי שנוצר משקף תמיד את התמהיל האמיתי.

### הגדרות

כל ההגדרות נקראות ממשתני סביבה, ואין בקוד שום סיסמה או מפתח. לשינוי ההגדרות יש
להעתיק את `.env.example` לקובץ `.env` ולערוך אותו. ברירת המחדל מתחברת ל-
`localhost\SQLEXPRESS` בהזדהות Windows, כך שאין צורך בסיסמה כלל.

## המסכים

**מסך הבית** הוא נקודת הכניסה אחרי ההתחברות. לעובד בנק הדם ולמנהל מוצגים כפתורי
קליטה וניפוק. לסטודנט מחקר מוצג מלאי מנוקה בלבד. בסרגל העליון מופיעים המסכים
המותרים לתפקיד, שם המשתמש המחובר וכפתור יציאה.

1. **קליטת תרומות** — סוג דם, תאריך תרומה, ת"ז ושם מלא של התורם. זמין למנהל ולעובד בנק הדם.
2. **ניפוק בשגרה** — סוג דם מבוקש ומספר מנות. המערכת מציגה המלצה לאישור, וכוללת סוג
   חלופי תואם כאשר אין מלאי מהסוג המבוקש.
3. **ניפוק אר"ן** — הוצאת כל מלאי ה-‎O-‎ הזמין, או שגיאה כאשר המלאי אזל.
4. **מלאי ולוג פעולות** — תמונת מצב של המלאי ותיעוד הפעולות. אצל סטודנט מחקר שמות
   התורמים ומספרי הזהות מוסתרים.
5. **יומן תיעוד** — תיעוד מלא לפי Part 11, כולל סינון, ייצוא ועותק XML. חסום לסטודנט מחקר.
6. **ניהול משתמשים ומטא-דאטה** — למנהל בלבד: יצירת חשבונות וצפייה בכמויות רשומות
   בלי תוכן קליני מזהה.

### ניווט

מסך פנימי אינו מציג ניווט משל עצמו, אלא כפתור חזרה למסך הבית בלבד. מפעיל שרוצה לעבור
לפעולה אחרת חייב לחזור לבית ולבחור אותה מחדש, ולכן אין מצב שבו הוא גולש בטעות מטופס
קליטה לתוך טופס ניפוק.

### שפת הצבעים

לכל כוונה קלינית צבע אחד, בכפתור שבמסך הבית, בפס הצבע שבראש המסך ובכפתור הפעולה:
ירוק מכניס מנות לבנק, כחול מוציא בשגרה, ואדום הוא חירום בלבד. אדום אינו משמש לקישוט,
ולכן מסך אדום תמיד מסמן משהו קליני חריג.

## אסטרטגיית הניפוק

זו ההחלטה המרכזית במערכת, והיא ממומשת ב-`core/allocation.py` לפי סדר העדיפויות הבא:

1. **התאמה מדויקת** לסוג הדם המבוקש. הבטוחה ביותר, ואינה מכלה מלאי של סוג אחר.
2. **סוג חלופי תואם**, בעדיפות לסוג השכיח יותר באוכלוסייה. סוג שכיח קל יותר להשלים,
   ולכן העלות של השימוש בו נמוכה.
3. **‎O-‎ תמיד אחרון**, גם כשהוא אינו הסוג הנדיר ביותר במלאי.

הכלל השלישי אינו נובע מהשכיחות אלא מהתפקיד: מקבל מסוג AB-‎ יכול לקבל מ-‎A-‎ (4%),
‏O-‎ (3%), B-‎ (2%) ו-‎AB-‎ (1%). מיון לפי שכיחות בלבד היה מציב את O-‎ במקום השני
ומכלה את רזרבת החירום, ולכן קיים כלל מפורש שדוחק אותו לסוף.

בתוך כל סוג דם, המנה הוותיקה ביותר נופקת ראשונה (FIFO), כנהוג בבנקי דם.

## תשובות לשאלות החשיבה שבמטלה

**למה רק ‎O-‎ מתאים לניפוק במצב אר"ן?**
באירוע רב נפגעים אין זמן לקבוע סוג דם ולבצע הצלבה. תאי הדם של ‎O-‎ אינם נושאים את
האנטיגנים A, B ו-RhD, ולכן הם אינם מעוררים תגובה חיסונית אצל אף מקבל. זה הסוג היחיד
שאפשר לתת לפצוע לא מזוהה בלי סיכון של תגובה המוליטית.

**איך זה משפיע על אסטרטגיית הניפוק בשגרה?**
‏O-‎ הוא כ-3% מהאוכלוסייה, אך הוא הדבר היחיד שעומד בין אירוע רב נפגעים לבין חוסר
יכולת לטפל בו. לכן הוא אינו סתם עוד סוג דם במלאי אלא רזרבה אסטרטגית: בשגרה המערכת
מנפקת אותו כמוצא אחרון בלבד, ומתריעה במפורש כאשר ניפוק בשגרה נוגע ברזרבה הזו.

  roles.py            שלושת התפקידים וההרשאות שלהם

  auth_service.py     התחברות וניהול משתמשים

## מודל הנתונים

| טבלה | תפקיד |
|---|---|
| `donors` | תורמים, לפי מספר תעודת זהות |
| `blood_units` | כל מנת דם בנפרד, עם קישור לתורם ולניפוק |
| `dispenses` | אירועי ניפוק, בשגרה או באר"ן |
| `activity_log` | לוג הפעולות |
| `app_users` | משתמשי המערכת, תפקידים וגיבוב סיסמאות |

**למה כל מנה נשמרת בנפרד ולא כמונה?** תוכנת BECS היא תוכנה רגולטורית שחייבת לאפשר
עקיבות. אם מתגלית בעיה במנה מסוימת, צריך להיות אפשר לדעת מאיזה תורם היא הגיעה ולאיזה
יעד היא נופקה. אילוץ בטבלה מבטיח שמנה נמצאת במלאי ללא ניפוק, או נופקה ומקושרת לניפוק
אחד בדיוק, ואין מצב ביניים.

## אמינות ואבטחה

- **טרנזקציות** — ניפוק כולו מתבצע או שכולו מתבטל. המנות ננעלות בזמן הבחירה
  (`UPDLOCK`), כך ששני מפעילים לא יכולים לנפק את אותה מנה.
- **חישוב מחדש בעת האישור** — התוכנית מחושבת שוב בצד השרת מול מלאי נעול, ולכן טופס
  שעבר מניפולציה אינו יכול לכפות ניפוק לא תואם.
- **אימות ת"ז** — ספרת הביקורת נבדקת, כדי שטעות הקלדה לא תשייך מנה לאדם אחר.
- **חסימת סתירה בסוג דם** — אם תורם רשום עם סוג דם אחר, הקליטה נחסמת ומתועדת. סוג דם
  של אדם אינו משתנה, ולכן סתירה כזו היא טעות שעלולה להעלות מנה מסומנת לא נכון על המדף.
- **שאילתות פרמטריות בלבד** — קלט לעולם אינו משורשר לתוך SQL.
- **הגנת CSRF** — לכל טופס טוקן ייחודי, כדי שלא ניתן יהיה להפעיל ניפוק מדף חיצוני.
- **התחברות לפי תפקיד** — כל מסך קליני דורש משתמש מחובר. הסיסמאות נשמרות כגיבוב בלבד.
- **הסתרת פרטים מזהים** — סטודנט מחקר אינו רואה שמות תורמים או מספרי זהות. ספירות מלאי
  לפי סוג דם נשארות גלויות כי הן אינן מזהות אדם.

## בדיקות

```powershell
python -m pytest
```

הבדיקות מכסות את טבלת התאימות, את אלגוריתם ההקצאה, את אימות הקלט, את יומן התיעוד
ואת הרשאות התפקידים. טבלת התאימות נבדקת מול כלל בלתי תלוי — עירוי בטוח בדיוק כאשר
התורם אינו נושא אנטיגן שאין למקבל — ולא מול העתק של עצמה.
